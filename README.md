## Задача 1. Обеспечить разработку

### Предлагаемое решение

Для организации разработки, хранения исходного кода, непрерывной
интеграции и непрерывной поставки предлагается использовать **GitLab**
(облачную версию GitLab.com) в сочетании с **GitLab CI/CD** и
собственными **GitLab Runner**.

GitLab предоставляет Git-репозитории, управление исходным кодом,
CI/CD-конвейеры, хранение переменных и секретов, а также инструменты для
управления процессом разработки. GitLab Runner выполняет задания сборки
и тестирования. При необходимости агенты можно установить на собственных
серверах компании.

Для хранения собранных Docker-образов можно использовать GitLab
Container Registry либо отдельный корпоративный Container Registry.

### 1. Хранение исходного кода и система контроля версий

Для каждого микросервиса создаётся отдельный Git-репозиторий. Например:

-   `users-service`;
-   `orders-service`;
-   `payments-service`;
-   `notifications-service`.

Такой подход позволяет независимо разрабатывать, тестировать, выпускать
и масштабировать сервисы. Для каждого репозитория можно настроить
собственные права доступа, правила слияния изменений и CI/CD-конвейеры.

GitLab поддерживает Git и предоставляет веб-интерфейс для работы с
ветками, Merge Request, коммитами и историей изменений.

### 2. Запуск сборки по событию из системы контроля версий

Для автоматического запуска сборки используется GitLab CI/CD.

В репозитории размещается файл `.gitlab-ci.yml`, в котором описываются
этапы сборки, тестирования и публикации приложения.

При push изменений или создании Merge Request GitLab автоматически
запускает pipeline согласно настроенным правилам. Таким образом, каждая
новая версия кода может проходить автоматические проверки до попадания в
основную ветку.

### 3. Запуск сборки вручную с указанием параметров

GitLab CI/CD поддерживает ручной запуск pipeline из веб-интерфейса.
Пользователь может запустить сборку и передать переменные, например:

-   `ENVIRONMENT` --- окружение (`dev`, `stage`, `prod`);
-   `VERSION` --- версия приложения;
-   `RUN_INTEGRATION_TESTS` --- необходимость запуска интеграционных
    тестов;
-   `DEPLOY` --- необходимость выполнения этапа развёртывания.

Параметры могут использоваться в заданиях pipeline для выбора
конфигурации и поведения сборки.

### 4. Настройки и шаблоны сборок

Настройки можно хранить на нескольких уровнях:

-   непосредственно в `.gitlab-ci.yml`;
-   в переменных проекта или группы;
-   в переменных, передаваемых при ручном запуске;
-   в подключаемых CI/CD-шаблонах.

Для разных конфигураций можно создавать отдельные jobs и stages,
использовать `rules`, `include` и переменные окружения.

Общие шаблоны pipeline можно вынести в отдельный репозиторий и
подключать к CI/CD-конфигурациям разных микросервисов. Это позволит
централизованно поддерживать стандарты сборки и не дублировать
одинаковые настройки.

### 5. Безопасное хранение секретных данных

GitLab CI/CD Variables позволяет хранить пароли, токены и ключи доступа
в настройках проекта или группы, не помещая их в исходный код.

Для чувствительных переменных следует использовать режим Masked, а для
ограничения области использования --- Protected и Environment scope.
Доступ к секретам необходимо предоставлять только тем pipeline и
пользователям, которым он действительно нужен.

Для более сложной инфраструктуры можно интегрировать GitLab с HashiCorp
Vault или облачным хранилищем секретов. В этом случае секреты будут
храниться централизованно, а задания CI/CD смогут получать их с учётом
настроенных политик доступа.

### 6. Несколько конфигураций сборки из одного репозитория

В одном репозитории можно описать несколько независимых jobs и
pipeline-конфигураций.

Например, для одного микросервиса можно организовать:

-   сборку и тестирование для разработки;
-   сборку релизного образа;
-   сборку образа для production;
-   запуск интеграционных тестов;
-   публикацию Docker-образа.

Выбор конфигурации выполняется с помощью переменных, правил `rules`,
условий запуска и отдельных jobs. Это позволяет использовать один
исходный код для нескольких сценариев сборки.

### 7. Пользовательские шаги и собственные Docker-образы сборки

GitLab CI/CD позволяет описывать произвольные команды в `script` и
`before_script`, а также использовать отдельные jobs для разных задач.

Для сборки можно применять собственные Docker-образы с заранее
установленными инструментами и зависимостями. Например, компания может
подготовить образ, содержащий нужную версию JDK, Maven, Node.js, Docker
CLI и дополнительные утилиты.

Это обеспечивает одинаковую среду сборки для разных разработчиков и
уменьшает вероятность ошибок, связанных с различиями в версиях
инструментов.

В production-среде для сборки Docker-образов следует отдельно продумать
безопасную настройку runner и способ доступа к Docker daemon. Необходимо
избегать выдачи избыточных привилегий недоверенным заданиям.

### 8. Собственные агенты сборки и параллельное выполнение

GitLab Runner можно развернуть на собственных серверах или виртуальных
машинах компании. Runner регистрируется в GitLab и получает задания из
очереди.

Можно создать несколько групп runner для разных типов задач:

-   сборка приложений;
-   модульное и интеграционное тестирование;
-   сборка Docker-образов;
-   публикация и развёртывание.

GitLab Runner поддерживает параллельное выполнение заданий. Количество
одновременно выполняемых jobs регулируется настройками runner и
доступными ресурсами серверов.

Параллельный запуск тестов можно организовать с помощью нескольких jobs,
`parallel` и `parallel:matrix`. Например, тестирование может выполняться
одновременно на нескольких версиях среды или для разных наборов тестов.

### Принцип взаимодействия компонентов

1.  Разработчик отправляет изменения в Git-репозиторий соответствующего
    микросервиса.
2.  GitLab получает событие и запускает pipeline по правилам
    `.gitlab-ci.yml`.
3.  GitLab Runner получает задание и запускает его в указанном
    Docker-образе.
4.  Выполняются сборка, статический анализ и тесты.
5.  При успешном прохождении проверок собирается Docker-образ.
6.  Образ публикуется в GitLab Container Registry.
7.  Для ручных запусков пользователь может указать параметры pipeline.
8.  Секретные значения передаются заданиям через защищённые CI/CD
    Variables или интеграцию с Vault.
9.  Несколько runner могут одновременно выполнять задания разных
    сервисов и параллельные тесты.

### Обоснование выбора

GitLab выбран по следующим причинам:

-   **Облачная система.** GitLab.com предоставляет облачную платформу,
    не требующую самостоятельного обслуживания основного сервера GitLab.
-   **Git и отдельные репозитории.** Поддерживается Git, а для каждого
    микросервиса можно создать отдельный репозиторий.
-   **Автоматический и ручной запуск.** Pipeline запускается по событиям
    Git и вручную с передачей переменных.
-   **Гибкая конфигурация.** Настройки сборок описываются в
    `.gitlab-ci.yml`, поддерживаются переменные, условия и шаблоны.
-   **Безопасное хранение секретов.** CI/CD Variables поддерживает
    маскирование и ограничение доступа к переменным.
-   **Несколько сценариев сборки.** Один репозиторий может содержать
    несколько jobs и конфигураций.
-   **Кастомные шаги и Docker-образы.** Можно выполнять произвольные
    команды и использовать собственные образы с инструментами сборки.
-   **Собственная инфраструктура выполнения.** GitLab Runner можно
    развернуть на серверах компании.
-   **Параллельность.** Несколько runner и параллельные jobs позволяют
    ускорить сборку и тестирование.

### Вывод по задаче 1

GitLab вместе с GitLab CI/CD, GitLab Runner и Container Registry
предоставляет единую платформу для хранения исходного кода,
автоматизации сборки, тестирования и публикации микросервисов. Облачная
управляющая платформа сочетается с возможностью выполнять задания на
собственной инфраструктуре компании.

## Задача 2. Логи

### Предлагаемое решение

Для централизованного сбора, хранения и анализа логов предлагается использовать **Elastic Stack (ELK Stack)**. В состав решения входят:

- **Filebeat** — лёгкий агент для сбора логов с хостов и контейнеров и их отправки в центральную систему.
- **Logstash** — обработка, фильтрация, преобразование и обогащение логов перед сохранением.
- **Elasticsearch** — централизованное распределённое хранилище и поисковый движок для индексирования и поиска записей.
- **Kibana** — пользовательский интерфейс для поиска, анализа, визуализации и сохранения запросов.

В Kubernetes Filebeat можно развернуть в виде DaemonSet, чтобы агент работал на каждом узле кластера и собирал логи контейнеров. Logstash принимает поток записей от агентов, при необходимости преобразует данные и передаёт их в Elasticsearch. Kibana предоставляет разработчикам и специалистам эксплуатации единый интерфейс для работы с логами.

### 1. Сбор логов со всех хостов

На каждом сервере устанавливается Filebeat. В Kubernetes Filebeat разворачивается в виде DaemonSet — по одному экземпляру на каждом подходящем узле.

Filebeat читает логи контейнеров из файлов, в которые среда контейнеризации записывает потоки `stdout` и `stderr`. Также агент может собирать системные журналы операционной системы и логи других компонентов инфраструктуры.

Для Kubernetes Filebeat может автоматически добавлять к записям метаданные: Namespace, имя Pod, контейнер и другие сведения. Это позволяет в дальнейшем фильтровать логи не только по тексту сообщения, но и по принадлежности к конкретному сервису или окружению.

### 2. Минимальные требования к приложениям

Приложения должны выводить сообщения в стандартные потоки `stdout` и `stderr`. Желательно использовать структурированный формат JSON и включать в записи следующие поля:

- время события;
- уровень логирования;
- название сервиса;
- окружение;
- идентификатор запроса или trace ID;
- текст сообщения.

Пример записи:

```json
{
  "timestamp": "2026-11-24T10:00:00Z",
  "level": "ERROR",
  "service": "orders-service",
  "environment": "production",
  "trace_id": "abc123",
  "message": "Database connection failed"
}
```

Структурированный формат упрощает обработку и поиск по отдельным полям. При этом приложению не требуется знать адрес Elasticsearch или самостоятельно отправлять данные в центральное хранилище. За сбор и передачу отвечает Filebeat.

### 3. Надёжная доставка логов

Для повышения надёжности доставки предлагается использовать Filebeat совместно с Logstash.

Схема доставки:

1. Filebeat считывает сообщения из `stdout`, `stderr` и системных журналов.
2. Агент отправляет записи в Logstash.
3. Logstash принимает сообщения, при необходимости разбирает JSON, нормализует поля, добавляет метаданные и выполняет фильтрацию.
4. После обработки Logstash передаёт записи в Elasticsearch.
5. Elasticsearch индексирует данные и делает их доступными для поиска через Kibana.

Для повышения надёжности необходимо настроить:

- дисковую очередь Filebeat (`queue.disk`), чтобы временно сохранять события при недоступности получателя;
- повторные попытки отправки при временных ошибках соединения;
- persistent queue в Logstash, чтобы сохранять принятые события на диске до их обработки и передачи дальше;
- несколько экземпляров Logstash за балансировщиком нагрузки для повышения доступности и пропускной способности;
- репликацию шардов Elasticsearch;
- мониторинг очередей, ошибок отправки и состояния компонентов.

При временной недоступности Elasticsearch Logstash может сохранять поступившие события в persistent queue и отправить их после восстановления хранилища. Filebeat, в свою очередь, использует собственную очередь для временного хранения данных на стороне источника.

При корректной настройке можно обеспечить доставку с семантикой at-least-once: события не подтверждаются источнику до успешной передачи на следующий этап, однако при повторной отправке возможны дубликаты. Поэтому необходимо контролировать заполнение дисковых очередей, свободное место и состояние всех компонентов.

Абсолютная гарантия доставки при любых отказах невозможна, особенно если одновременно потеряны источник и его локальный буфер.

### 4. Центральное хранилище и поиск

В качестве центрального хранилища используется Elasticsearch.

Elasticsearch индексирует поступающие записи и предоставляет распределённый полнотекстовый поиск, фильтрацию и агрегацию данных. Можно искать логи по следующим параметрам:

- названию микросервиса;
- уровню ошибки;
- временному интервалу;
- окружению;
- Namespace и Pod;
- идентификатору запроса;
- тексту сообщения;
- другим полям JSON-документа.

Для разных сервисов и окружений можно использовать отдельные индексы или data streams. Для управления сроком хранения данных рекомендуется применять Index Lifecycle Management (ILM): например, перемещать старые индексы на более дешёвые узлы хранения, а по истечении заданного срока удалять их.

Для повышения отказоустойчивости Elasticsearch разворачивается в виде кластера из нескольких узлов. Реплики шардов позволяют сохранить доступность данных при отказе отдельного узла, если кластер спроектирован с учётом размещения реплик на разных узлах.

### 5. Пользовательский интерфейс и доступ разработчиков

Для работы с логами используется Kibana.

В Kibana разработчики и специалисты эксплуатации могут:

- выполнять поисковые запросы в Discover;
- фильтровать записи по полям;
- выбирать временной диапазон;
- просматривать подробности отдельных событий;
- создавать визуализации и dashboards;
- сохранять поисковые запросы и представления.

Для разграничения доступа используются механизмы безопасности Elastic Stack: пользователи, роли и пространства Kibana (Spaces).

Например, разработчикам можно предоставить доступ к логам своих сервисов и окружений `development` и `staging`, ограничив доступ к production-данным.

Права следует выдавать по принципу минимально необходимых привилегий. При необходимости чувствительные поля логов можно исключать или маскировать до передачи данных в Elasticsearch.

### 6. Сохранение поиска и передача ссылки

Kibana позволяет сохранять поисковые запросы в Discover, а также dashboards и другие объекты. Сохранённым поиском можно поделиться с коллегами с помощью ссылки.

Например, разработчик может сохранить запрос, который отображает все ошибки сервиса `orders-service` за выбранный временной интервал, и отправить ссылку команде для совместного анализа инцидента.

Получатели должны иметь собственные учётные записи и соответствующие права доступа к Kibana и данным. Ссылка на сохранённый поиск не должна обходить настроенные механизмы авторизации.

### Принцип взаимодействия компонентов

1. Микросервисы записывают логи в `stdout` и `stderr`.
2. Filebeat на каждом узле собирает контейнерные и, при необходимости, системные логи.
3. Filebeat добавляет метаданные хоста и Kubernetes и отправляет записи в Logstash.
4. Logstash обрабатывает, фильтрует и обогащает записи, используя настроенные pipeline.
5. Elasticsearch индексирует записи и хранит их в кластере.
6. Kibana подключается к Elasticsearch и предоставляет интерфейс для поиска, фильтрации и визуализации логов.
7. Разработчики сохраняют поисковые запросы и dashboards и делятся ссылками с коллегами в рамках предоставленных им прав доступа.

### Обоснование выбора

Elastic Stack выбран по следующим причинам:

- **Централизованный сбор.** Filebeat можно установить на всех хостах, а в Kubernetes развернуть как DaemonSet для сбора логов со всех узлов.
- **Минимальные требования к приложениям.** Достаточно выводить сообщения в `stdout` и `stderr`; приложению не нужно самостоятельно отправлять данные в хранилище.
- **Надёжность доставки.** Дисковая очередь Filebeat, persistent queue Logstash, повторные попытки отправки и репликация Elasticsearch снижают риск потери логов при временных отказах.
- **Обработка данных.** Logstash позволяет разбирать, фильтровать, нормализовать и обогащать записи перед индексированием.
- **Поиск и фильтрация.** Elasticsearch поддерживает полнотекстовый поиск, фильтры и агрегации по полям логов.
- **Пользовательский интерфейс.** Kibana предоставляет инструменты для поиска, анализа и визуализации логов.
- **Сохранённые запросы.** Поиски и dashboards можно сохранять и передавать коллегам по ссылке.
- **Разграничение доступа.** Роли и Spaces позволяют ограничивать доступ разработчиков к данным сервисов и окружений.
- **Масштабирование.** Filebeat, Logstash и Elasticsearch можно масштабировать независимо в зависимости от объёма логов и нагрузки.

### Вывод по задаче 2

Elastic Stack на базе Filebeat, Logstash, Elasticsearch и Kibana обеспечивает централизованный сбор, обработку, хранение и анализ логов микросервисной системы.

Приложениям достаточно выводить сообщения в стандартные потоки, а агенты Filebeat собирают их со всех хостов и передают в центральную систему. Elasticsearch обеспечивает индексирование и поиск, а Kibana предоставляет разработчикам единый интерфейс для анализа логов, сохранения запросов и совместного разбора инцидентов.

## Задача 3. Мониторинг

### Предлагаемое решение

Для мониторинга состояния хостов и микросервисов предлагается
использовать **Prometheus** и **Grafana**.

Дополнительно применяются:

-   **Node Exporter** --- сбор метрик операционной системы и ресурсов
    хостов;
-   **cAdvisor** --- сбор метрик использования ресурсов контейнерами;
-   **kube-state-metrics** --- сбор метрик состояния объектов
    Kubernetes;
-   **экспортёры и встроенные endpoints приложений** --- сбор метрик,
    специфичных для микросервисов;
-   **Alertmanager** --- обработка и отправка уведомлений о проблемах.

Prometheus собирает и хранит временные ряды метрик, а Grafana
используется для запросов, агрегации данных и построения настраиваемых
панелей мониторинга.

### 1. Сбор метрик со всех хостов

На каждом сервере устанавливается Node Exporter. Он предоставляет
метрики операционной системы по HTTP, которые периодически опрашиваются
Prometheus.

В Kubernetes Node Exporter обычно разворачивается как DaemonSet, чтобы
собирать метрики каждого узла кластера.

Prometheus автоматически обнаруживает targets через настройки service
discovery Kubernetes. Это позволяет добавлять новые узлы и сервисы без
необходимости вручную прописывать каждый адрес.

### 2. Метрики ресурсов хостов

Node Exporter собирает системные метрики, необходимые для контроля
состояния серверов:

-   **CPU:** загрузка процессора, время работы в разных режимах;
-   **RAM:** общий объём, свободная и используемая память;
-   **HDD:** объём файловых систем, свободное место, статистика операций
    ввода-вывода;
-   **Network:** сетевой трафик, количество переданных и полученных
    байт, ошибки интерфейсов.

Эти показатели позволяют оценивать загрузку инфраструктуры, выявлять
нехватку ресурсов и находить узкие места.

### 3. Метрики ресурсов отдельных сервисов

Для сбора метрик контейнеров используется cAdvisor. Он предоставляет
информацию об использовании CPU, памяти, сети и файловой системы
контейнерами.

В Kubernetes эти данные могут поступать через kubelet и его endpoints.
Prometheus собирает метрики и связывает их с контейнерами и Pod.

Для получения информации о состоянии объектов Kubernetes используется
kube-state-metrics. Он предоставляет данные о количестве Pod, их
состоянии, перезапусках, Deployment, ReplicaSet и других ресурсах.

Таким образом, можно анализировать потребление ресурсов не только на
уровне всего хоста, но и отдельно для каждого микросервиса.

### 4. Метрики, специфичные для сервисов

Для мониторинга бизнес- и прикладных показателей каждый микросервис
должен предоставлять endpoint с метриками в формате Prometheus, обычно
`/metrics`.

В зависимости от назначения сервиса можно собирать:

-   количество HTTP-запросов;
-   количество ошибок;
-   задержку обработки запросов;
-   количество активных соединений;
-   число операций в очереди;
-   время выполнения фоновых задач;
-   количество успешных и неуспешных бизнес-операций.

Для приложений можно использовать Prometheus Client Libraries для
соответствующего языка программирования.

Например, сервис заказов может публиковать количество созданных заказов,
число ошибок обработки и время ответа API. Это позволит отслеживать не
только состояние инфраструктуры, но и качество работы самих
микросервисов.

### 5. Запросы и агрегация информации

Prometheus предоставляет язык запросов **PromQL**. С его помощью можно
выбирать, фильтровать и агрегировать метрики.

Например, запрос для получения средней загрузки CPU по узлам:

``` promql
100 * (1 - avg by (instance) (
  rate(node_cpu_seconds_total{mode="idle"}[5m])
))
```

Запрос для получения текущего потребления памяти контейнерами:

``` promql
container_memory_working_set_bytes
```

Метрики можно агрегировать по узлам, Namespace, Pod, сервисам и другим
меткам.

Grafana предоставляет пользовательский интерфейс для выполнения запросов
к Prometheus и отображения результатов в виде графиков, таблиц и других
визуализаций.

### 6. Настраиваемые панели мониторинга

В Grafana можно создавать отдельные dashboards для разных задач и
команд.

Например:

-   **Infrastructure Overview** --- общая загрузка CPU, RAM, дисков и
    сети;
-   **Kubernetes Cluster** --- состояние узлов, Pod, Deployment и
    Namespace;
-   **Microservices Overview** --- количество запросов, ошибки и
    задержки каждого сервиса;
-   **Service Details** --- подробные метрики конкретного микросервиса;
-   **Business Metrics** --- прикладные показатели работы системы.

Панели можно настраивать под конкретные команды, сервисы и окружения.
Доступ к dashboards регулируется с помощью пользователей, команд и ролей
Grafana.

### 7. Оповещения о проблемах

Для своевременного обнаружения проблем предлагается использовать
Alertmanager совместно с Prometheus.

В Prometheus задаются правила оповещений, например:

-   высокая загрузка CPU в течение заданного периода;
-   нехватка свободной оперативной памяти;
-   заполнение дискового пространства;
-   недоступность узла или сервиса;
-   большое количество HTTP 5xx;
-   превышение допустимой задержки ответа.

Alertmanager группирует и маршрутизирует уведомления в настроенные
каналы, например электронную почту или корпоративный мессенджер.

### Принцип взаимодействия компонентов

1.  Node Exporter собирает метрики операционной системы каждого хоста.
2.  cAdvisor предоставляет метрики использования ресурсов контейнерами.
3.  kube-state-metrics собирает информацию о состоянии объектов
    Kubernetes.
4.  Микросервисы публикуют собственные метрики через endpoint
    `/metrics`.
5.  Prometheus обнаруживает targets и периодически опрашивает их.
6.  Prometheus сохраняет временные ряды и предоставляет PromQL для
    запросов и агрегации.
7.  Grafana получает данные из Prometheus и отображает их на
    настраиваемых dashboards.
8.  Правила оповещений Prometheus передают события в Alertmanager,
    который отправляет уведомления ответственным специалистам.

### Обоснование выбора

Prometheus и Grafana выбраны по следующим причинам:

-   **Сбор метрик со всех хостов.** Node Exporter устанавливается на
    серверах и предоставляет системные метрики.
-   **Мониторинг CPU, RAM, HDD и Network.** Node Exporter собирает
    показатели ресурсов операционной системы.
-   **Метрики отдельных сервисов.** cAdvisor предоставляет метрики
    контейнеров, а kube-state-metrics --- состояние объектов Kubernetes.
-   **Прикладные метрики.** Микросервисы могут самостоятельно
    публиковать метрики в формате Prometheus.
-   **Запросы и агрегация.** PromQL позволяет фильтровать и агрегировать
    временные ряды.
-   **Пользовательский интерфейс.** Grafana предоставляет удобный
    интерфейс для запросов и визуализации.
-   **Настраиваемые панели.** Можно создавать dashboards для
    инфраструктуры, Kubernetes, отдельных микросервисов и
    бизнес-показателей.
-   **Оповещения.** Prometheus и Alertmanager позволяют обнаруживать
    проблемы и уведомлять ответственных специалистов.
-   **Масштабируемость.** Архитектуру можно расширять новыми
    экспортёрами, сервисами и источниками метрик.

### Вывод по задаче 3

Prometheus в сочетании с Node Exporter, cAdvisor, kube-state-metrics и
прикладными экспортёрами обеспечивает сбор метрик инфраструктуры и
микросервисов. Grafana предоставляет единый интерфейс для анализа данных
и настройки панелей мониторинга, а Alertmanager помогает своевременно
реагировать на отклонения.
